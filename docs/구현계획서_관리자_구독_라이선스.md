# 관리자 구독 및 라이선스 구현계획서

## 1. 목표와 화면 역할

관리자가 전체 구독과 라이선스의 상태를 파악하고, 만료·기기 초과·인증 문제를 찾아 조치할 수 있게 한다. 한 사용자의 요금제를 바꾸는 작업은 기존 **사용자 관리 → 사용자 상세 → 요금제 변경**을 유지한다.

| 위치 | 주된 질문 | 기능 |
| --- | --- | --- |
| 사용자 관리 | 이 사용자의 현재 플랜은 무엇인가? | 프로필, 현재 플랜, 시작·만료일, 플랜 변경, 해당 사용자 세션 종료 |
| 구독 및 라이선스 | 지금 전체 서비스에서 어떤 구독·기기에 조치가 필요한가? | 전체 현황, 검색·필터, 만료 예정, 구독 상세·이력, 기기 현황·해제, 운영 기록 |
| 결제 현황 | 실제로 얼마가 승인·환불되었는가? | 결제 원장과 PG 연동 후 별도 구현. 구독 금액이나 관리자가 만든 번호로 결제를 추정하지 않음 |

구독 탭에서 사용자 이름을 누르면 사용자 상세로 이동하고, 플랜 변경은 기존 변경 UI와 API를 재사용한다. 두 화면에 서로 다른 플랜 변경 규칙을 만들지 않는다.

## 2. 현재 구현 기준

- `/admin?tab=subscriptions`는 준비 중 안내만 있다 (`frontend/src/app/admin/page.tsx`). 대시보드의 MRR·신규 결제 값도 고정값이다.
- 사용자 상세에는 플랜 변경과 활성 세션 종료 UI가 있다. 플랜 변경은 SUPER 관리자 전용 `POST /api/admin/users/plan`에서 사유를 받고 트랜잭션으로 처리한다.
- `subscriptions`가 구독과 라이선스 정보를 함께 보유한다. `license_activations`는 구독별 기기 활성화 기록이다. 따라서 독립 라이선스 발급 시스템을 새로 설계하지 않는다.
- 관리자 수동 플랜 부여 시 `payment_no`에 `ADMIN-FREE-*` 또는 `ADMIN-PAID-*`가 들어가지만 실제 수납 금액은 0이다. 사용자 유료 셀프 구독도 결제 승인 연동 전에는 막혀 있다. `payment_no`, `price_amount`, `license_key`만으로 결제 성공이나 MRR을 판단하지 않는다.
- 사용자별 `user_audit_logs`가 있고 플랜 변경 사유를 저장한다. 기존 감사 로그 API와 기기 종료 경로는 구현 전 상세 검증이 필요하다.

## 3. 화면 명세

### 3.1 전체 현황

- 카드: 활성 구독 수, 7일·30일 내 만료 수, 만료되었으나 활성으로 남은 수, 활성 기기 수, 허용 대수 초과 수.
- 각 카드는 같은 기준의 목록 필터로 이동한다. 집계 시 `plan_status`, `is_active`, `current_period_end`를 함께 검사하고 Reader·무료 체험·관리자 부여를 구분한다.
- 마지막 갱신 시각, 조회 실패 상태, 빈 결과 상태를 표시한다. 결제 근거가 마련되기 전 MRR·결제 건수는 이 화면에서 제외하고 기존 대시보드 고정값도 제거하거나 `준비 중`으로 바꾼다.

### 3.2 구독 목록

- 열: 사용자 이메일, 플랜, 부여 유형(체험·관리자 무료·관리자 유료·실결제 등 확인 가능한 값), 구독 상태, 시작·만료일, 결제 주기, 활성 기기 수/허용 대수, 최근 변경일.
- 검색: 이메일 또는 사용자 ID. 필터: 상태, 플랜, 부여 유형, 만료 예정 기간, 기기 초과 여부. 서버 기준 정렬·페이지네이션을 적용하고 URL 검색 조건을 유지한다.
- 상태 배지는 DB 값만 반복하지 않는다. `ACTIVE`여도 만료 시각이 지났으면 `만료 처리 필요`로 표시한다. 비활성·취소·만료 및 기기 초과를 구분한다.
- 행 선택 시 구독 상세를 열고 사용자 상세로 이동할 수 있다. 목록에서 라이선스 키·검증 키·결제 번호 원문을 노출하지 않는다.

### 3.3 구독 상세와 이력

- 현재 구독의 ID, 플랜, 상태, 기간, 허용 기기 수, 생성·변경 시각, 부여 유형을 표시한다.
- 해당 사용자의 과거 구독 레코드와 `PLAN_CHANGE` 감사 로그를 시간순으로 묶어 표시한다. 기록마다 변경자·사유·시각을 확인할 수 있어야 한다. 구독 레코드만으로 정확한 이전/이후 값을 복원할 수 없는 항목은 빈칸 또는 `기록 없음`으로 표시한다.
- 플랜 변경 버튼은 기존 사용자 관리 변경 흐름으로 연결한다. 별도 기간 연장·상태 강제 변경은 감사 기록과 경합 제어 규칙이 마련된 뒤 추가한다.

### 3.4 라이선스·기기 운영

- 구독별 활성 기기 이름, 기기 ID 일부, 활성화 시각, 마지막 확인 시각(데이터가 있는 경우), 상태를 표시한다.
- 개별 기기 해제와 전체 기기 해제는 대상·영향을 보여 주고 사유를 입력받는다. 서버에서 관리자 권한, 대상 소유 관계, 현재 상태를 다시 확인한 뒤 트랜잭션으로 비활성화하고 감사 로그를 남긴다.
- 해제 뒤 클라이언트의 다음 검증 요청에서 접근 차단이 되는지 확인한다. 즉시 차단이 필요한 제품 요구라면 검증 주기와 캐시 무효화까지 별도로 설계한다.
- 기기 수는 활성 구독에 연결된 `is_active=true` 기록 기준으로 집계한다. 과거 구독의 활성 기록이 남아 있는 경우 별도 이상 상태로 표시한다.

## 4. API와 데이터 작업

1. `GET /api/admin/subscriptions`: 집계와 목록을 서버에서 조회. 검색·필터·정렬·페이지 크기 검증, 관리자 인증, `no-store` 적용.
2. `GET /api/admin/subscriptions/[id]`: 구독 상세, 같은 사용자의 구독 이력, 기기 목록, 관련 감사 로그 조회. 민감한 키 값은 기본 응답에서 제외.
3. `POST /api/admin/subscriptions/[id]/devices/[deviceId]/deactivate`: SUPER 관리자 권한, 필수 사유, 소유 관계 확인, 재요청 안전성, 감사 기록을 포함한 트랜잭션. 전체 해제도 별도 명시적 동작으로 제공.
4. 기존 사용자 관리의 세션 종료 API와 감사 로그 API를 점검해 인증·권한·소유 관계·사유 정책을 통일한다. 중복 구현이 있으면 공용 서버 함수로 모은다.
5. 필요 시 `license_activations`에 `last_seen_at`을 추가한다. 현재 확인 시각을 신뢰할 수 없다면 UI에서 표시하지 않는다. 목록 조회용 인덱스와 활성 구독 유일성 제약은 실제 운영 데이터의 중복을 조사한 뒤 마이그레이션한다.
6. 감사 로그는 기존 `user_audit_logs`를 우선 재사용한다. 기기 해제·전체 해제에 대한 액션 코드와 구독/기기 ID를 구조화해 남길 수 있는지 스키마를 확인하고, 사유 문자열에만 식별자를 넣어야 한다면 컬럼 추가를 검토한다.
7. Next.js API 외에 배포 중인 Cloudflare Functions 경로도 확인한다. 같은 관리자 기능이 두 런타임 모두 필요하면 동등한 인증·응답·감사 처리를 구현한다.

## 5. 결제와 매출의 별도 조건

- 실제 결제 내역은 PG 승인·취소·환불 웹훅과 내부 결제 원장, 거래 ID 중복 방지, 금액·통화·상태 검증이 연결된 뒤 제공한다.
- MRR은 승인된 반복 결제의 기간 배분, 환불, 무료/관리자 부여 제외 규칙을 합의한 뒤 계산한다. `subscriptions.price_amount` 합계는 MRR이 아니다.
- 그전에는 구독 상세의 `payment_no`를 결제 증빙으로 표시하지 않으며, 화면에는 `결제 연동 전` 또는 `수동 부여`처럼 확인된 사실만 표시한다.

## 6. 구현 순서와 완료 기준

| 단계 | 구현 | 완료 기준 |
| --- | --- | --- |
| 1 | 현재 데이터·런타임 점검, 상태/부여 유형 정의, 조회 API | 관리자만 조회 가능하고 활성·만료·Reader·관리자 부여 표본이 정확히 분류됨 |
| 2 | 구독 탭 현황·목록·상세·이력 | 검색·필터·페이지 이동이 서버 결과와 일치하고 사용자 상세로 연결됨 |
| 3 | 기기 해제와 감사 기록 | 타 사용자 기기 조작 차단, 재요청 안전, 사유·관리자·대상 기록, 다음 인증 검증에서 해제 반영 |
| 4 | 사용자 관리 중복 정리, 대시보드 허위 결제 수치 제거 | 플랜 변경 규칙은 한 경로로 유지되고 결제처럼 보이는 고정 수치가 없음 |
| 5 | PG/결제 원장 연동 후 결제 내역·MRR | 승인·취소·환불 사례를 원장과 대조해 수치가 일치함 |

검증에는 관리자/일반 사용자 권한, 구독 없음, 만료 경계 시각, 동시 플랜 변경, 오래된 활성 기기, 기기 초과, 중복 해제 요청을 포함한다. 단계 1~4는 결제 서비스 없이 구현할 수 있으며, 단계 5는 결제 공급자와 승인 데이터가 준비되어야 한다.
