# 블로그 공개 발행 및 페이지 개선 구현계획서

작성일: 2026-09-27  
대상: 웹 블로그(`/blog`, `/blog/[slug]`), 에디터 초안 저장, 관리자 블로그 관리

## 1. 목표와 완료 기준

- 관리자가 승인한 글은 다른 기기와 비로그인 브라우저에서도 같은 내용으로 열린다.
- 초안은 공개 목록, 상세 주소, 사이트맵에 노출되지 않는다.
- 공개 글은 고유한 `/blog/{slug}` 주소, 제목·설명·대표 이미지·canonical 메타데이터를 갖는다.
- 웹의 정적 빌드가 통과하고, 발행·수정·비공개 전환 후 배포 상태를 관리자가 확인할 수 있다.
- 에디터의 발행 전 미리보기와 실제 블로그 본문은 같은 마크다운 기능을 표시한다.

## 2. 현재 구조와 제약

| 영역 | 현재 상태 | 결과 |
| --- | --- | --- |
| 저장소 | `blogData.ts`가 게시글을 브라우저 `localStorage`에 저장 | 한 관리자의 발행 내용이 다른 방문자에게 전달되지 않음 |
| 배포 | Next.js `output: 'export'` + Cloudflare Pages | 새 상세 경로를 공개하려면 빌드와 배포가 필요 |
| 상세 페이지 | 클라이언트 컴포넌트의 `[slug]` 경로, `generateStaticParams` 없음 | 현재 정적 웹 빌드의 차단 요인 |
| 검색 노출 | 블로그 전용 메타데이터 없음, 상위 canonical은 `/`, 사이트맵에 블로그 없음 | 개별 글의 검색 노출과 공유 미리보기가 부정확함 |
| 본문 표시 | 상세 페이지는 `react-markdown` + GFM만 사용 | 에디터의 수식·Mermaid와 결과가 다름 |

관련 코드: `frontend/src/lib/blogData.ts`, `frontend/src/app/blog/page.tsx`, `frontend/src/app/blog/[slug]/page.tsx`, `frontend/src/app/admin/components/BlogTab.tsx`, `frontend/src/components/BlogPostModal.tsx`, `frontend/src/app/sitemap.ts`.

## 3. 기본 아키텍처 결정

기존 정적 배포를 유지한다. **Supabase를 게시글 원본 저장소로 사용**하고, 관리자 발행·수정·비공개 전환 시 서버 측 API가 기록한 뒤 Cloudflare Pages 재배포를 요청한다. 빌드가 공개 대상으로 지정된 글의 슬러그와 고정된 본문 버전을 읽어 목록·상세 HTML 및 메타데이터를 생성한다. 이 방식의 공개 시점은 관리자가 버튼을 누른 순간이 아니라 **새 배포가 성공한 순간**이다. 관리자 화면에는 `초안 → 배포 대기 → 공개` 상태를 구분한다.

정적 배포에서 새 슬러그를 실행 중에 추가할 수 없으므로, 배포 훅을 호출한 것만으로 발행 성공을 표시하지 않는다. 재배포 실패 시 기존 공개 사이트는 유지하고 관리자에게 실패·재시도 상태를 보여준다. 즉시 공개가 필수 요구사항으로 확정되면 별도 작업으로 블로그를 서버 렌더링 가능한 런타임으로 옮긴다. 그때는 정적 재배포 흐름을 중복 구현하지 않는다.

설계 근거: [Next.js `generateStaticParams`](https://nextjs.org/docs/app/api-reference/functions/generate-static-params), [Cloudflare Pages Deploy Hooks](https://developers.cloudflare.com/pages/configuration/deploy-hooks/).

## 4. 단계별 구현

### 1단계 — 공용 데이터와 권한

1. `blog_posts` 테이블을 만든다. 필드: `id`(UUID), `slug`(유일 인덱스), `category`, `author_id`, `is_featured`, `desired_public`(공개 의도), `deployment_status`(`pending`/`live`/`failed`), `target_revision_id`, `live_revision_id`, `created_at`, `updated_at`. 제목·요약·본문·커버·태그·발행일은 변경 불가능한 `blog_post_revisions`에 보관해 빌드 중 내용이 바뀌지 않게 한다.
2. 일반 방문자의 DB 직접 읽기·쓰기는 허용하지 않는다. 공개 페이지는 생성된 정적 HTML을 제공하고, 빌드와 관리자 API만 필요한 DB 접근 권한을 가진다. 작성·수정·발행·비공개·삭제는 관리자 인증과 역할 확인을 거치는 서버 API에서 수행한다. Service Role 키와 배포 훅 URL은 서버 환경변수에만 둔다. 기존 `/api/admin/_shared.js`의 관리자 검증을 재사용하되, 발행 API의 MFA 요구 수준도 서버에서 확인한다.
3. 클라이언트의 `localStorage`는 게시글 원본 저장소에서 제거한다. 에디터 초안 저장과 관리자 목록은 공용 API를 사용한다. 네트워크 실패를 발행 성공으로 표시하지 않는다.
4. 이미지 업로드가 필요하면 Supabase Storage에 허용 형식·용량·관리자 권한을 적용한다. 외부 이미지 URL은 유효성 검사와 실패 시 기본 커버를 유지한다.

**검증:** 기기 A에서 초안 작성 후 기기 B의 관리자 계정에서 조회 가능; 일반 방문자는 초안을 조회할 수 없음; 중복 슬러그 저장은 명확한 오류로 반환.

### 2단계 — 배포 가능한 목록·상세 페이지

1. `[slug]/page.tsx`를 서버 페이지와 상호작용용 클라이언트 컴포넌트로 분리한다. 빌드 시 `desired_public = true`인 슬러그 목록을 읽어 `generateStaticParams`로 반환한다. `dynamicParams = false`를 적용해 배포되지 않은 주소는 404로 처리한다.
2. `/blog` 목록과 상세 본문은 같은 공개 대상 스냅샷을 사용한다. 빌드 시작 시 각 글의 `target_revision_id`를 고정하고 그 버전만 목록·상세·사이트맵에 사용한다. 빌드에 필요한 환경변수가 없거나 조회가 실패하면 이전 데이터로 조용히 대체하지 말고 빌드를 실패시킨다.
3. `frontend/web-build.js`와 `frontend/desktop-build.js`의 웹·데스크톱 빌드 대상별 처리 범위를 확인한다. 블로그 데이터 조회는 웹 빌드에만 필요하며 데스크톱 패키징을 막지 않아야 한다.
4. 기존 초기 게시글(`INITIAL_BLOG_POSTS`)은 한 번만 DB로 이관한다. 이관 후 코드 상수와 DB를 동시에 공개 원본으로 사용하지 않는다.

**검증:** 정적 빌드 통과; 생성된 `out/blog/...` HTML 존재; 직접 주소 입력과 새로고침 작동; 미발행 슬러그는 404.

### 3단계 — 발행 및 재배포 상태

1. 관리자 발행 요청은 새 리비전을 `target_revision_id`로 지정하고 `desired_public = true`, `deployment_status = pending`으로 기록한 뒤 배포를 요청한다. 배포 훅 호출 실패 시 `failed` 상태와 재시도 동작을 남긴다. 여러 글을 연속 수정할 때 재배포 요청을 묶어 불필요한 빌드 폭주를 막는다.
2. 배포 성공 여부는 Cloudflare의 배포 상태 또는 빌드 파이프라인 콜백으로 확인한다. 성공한 빌드 스냅샷의 리비전만 `live_revision_id`로 확정하고 `deployment_status = live`로 바꾼다. 관리자는 마지막 배포 시각, 대기·실패 상태, 재시도 버튼을 본다. 배포 중 새 편집이 발생하면 새 리비전은 다음 배포로 보내며 완료 콜백이 더 최신 변경을 덮어쓰지 못하게 한다.
3. 비공개 전환과 삭제도 재배포 후 공개 사이트에서 사라졌는지 확인한다. 삭제는 우선 소프트 삭제 또는 초안 전환으로 처리해 실수 복구가 가능하게 한다.
4. 에디터의 버튼 문구를 실제 동작에 맞춰 `초안 저장`으로, 관리자 버튼을 `공개 배포 요청`으로 정리한다. 배포 전에는 “공식 블로그에 라이브 노출 중”이라고 표시하지 않는다.

**검증:** 발행 전·배포 중·배포 후 상태가 실제 방문자 화면과 일치; 빌드 실패 시 허위 성공 안내 없음; 비공개 후 새 배포에서 목록·상세·사이트맵에서 제거.

### 4단계 — 검색 노출과 주소

1. `/blog` 전용 메타데이터를 추가하고, 각 상세 페이지에서 `generateMetadata`로 제목·설명·Open Graph·Twitter 이미지·canonical을 생성한다. 상위 레이아웃의 홈페이지 canonical이 블로그에 상속되지 않도록 명시한다.
2. `sitemap.ts`에 현재 빌드 스냅샷의 공개 대상 글만 넣는다. `lastModified`에는 해당 리비전의 실제 수정 시각을 사용한다. 초안은 포함하지 않는다. 배포 전 글의 사이트맵은 새 배포 전까지 공개되지 않는다.
3. 슬러그 생성 규칙과 중복 검사를 공통화한다. 공개 후 슬러그 변경이 필요하면 이전 주소에서 새 주소로 이동하는 별도 매핑을 만든다.
4. 검색·카테고리 선택을 URL 쿼리와 양방향 동기화해 새로고침과 링크 공유 시 같은 목록이 보이게 한다.

**검증:** 글마다 고유한 HTML `<title>`, 설명, canonical, 공유 이미지가 생성됨; 사이트맵은 공개 글만 포함; 필터 링크 공유·뒤로 가기 작동.

### 5단계 — 본문 표시와 사용성

1. 에디터의 블로그 미리보기와 공개 상세 페이지가 공통 렌더러를 사용하도록 정리한다. GFM 표·체크리스트, 코드 블록, 수식(KaTeX), Mermaid의 지원 범위를 명시하고 같은 샘플 문서로 비교한다.
2. 외부 링크·이미지와 본문 HTML은 안전하게 처리한다. 이미지 실패 시 기본 커버로 바꾸되 기본 커버도 실패했을 때 재시도 루프가 생기지 않도록 한다.
3. 모바일에서 긴 제목·코드 블록·표의 가로 넘침, 검색 입력 접근성, 복사 버튼의 실패 안내를 확인한다.
4. 날짜는 내부 저장에 ISO 형식을 쓰고 화면에만 `YYYY.MM.DD`로 표시한다. 읽는 시간은 발행 데이터와 본문 변경 시 함께 갱신한다.

**검증:** 같은 글이 에디터 미리보기와 공개 페이지에서 주요 요소별로 일치; 좁은 화면에서 가로 스크롤이 페이지 전체로 번지지 않음.

## 5. 마이그레이션과 검증 순서

1. DB 스키마·권한을 준비하고 초기 4개 글을 이관한다. 기존 `localStorage` 글은 **자동 공개하지 않는다**. 관리자에게 가져오기 목록으로 보여 검토 후 선택 이관한다.
2. 공용 API를 연결한 뒤 기존 읽기 경로를 제거한다. 중복 ID·슬러그, 누락된 필드, 잘못된 이미지 URL을 이관 시 검증한다.
3. 정적 빌드, 공개 글 직접 접속, 비공개 접근 차단, 메타데이터·사이트맵, 모바일 본문 표시를 검증한다.
4. 스테이징에서 관리자 발행 → 재배포 → 다른 브라우저 공개 확인 → 비공개 → 재배포 → 404 확인까지 한 사이클을 완료한 뒤 운영 적용한다.

## 6. 작업 순서와 범위

| 순서 | 산출물 | 선행 조건 |
| --- | --- | --- |
| P0 | DB 스키마·권한·관리자 API, 초기 글 이관 | 기존 관리자 인증 방식 확인 |
| P0 | 정적 상세 경로 및 목록 빌드 복구 | 공개 데이터 조회 가능 |
| P0 | 배포 상태 연동과 실패 재시도 | Cloudflare 배포 훅·상태 조회 자격증명 |
| P1 | 글별 메타데이터·사이트맵·필터 URL | 공개 상세 경로 안정화 |
| P1 | 공통 마크다운 렌더러·모바일 품질 | 실제 콘텐츠 샘플 확정 |

이 계획서는 구현 전 설계안이다. DB 변경, Cloudflare 비밀값 설정, 운영 배포는 이 문서 작성만으로 수행하지 않는다.
